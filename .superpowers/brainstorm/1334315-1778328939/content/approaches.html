ECC Agents — 3 Approaches

How to model founder-level agents in the schema and surface them in the UI

A

Nullable companyId in agents table

Allow agents.companyId to be nullable. ECC agents have no company. Auto-seeded on first ECC spawn if missing. Status driven by polling workflow_runs for ecc_conversation type.

Pros

  • Reuses existing agents infrastructure (budget, heartbeat, status)
  • No new table or migration beyond one column change
  • Agents page can list ECC agents naturally

Cons

  • Schema change affects all code that assumes companyId not null
  • Needs care to exclude from company-scoped agent queries

✅ Recommended — minimal schema impact, maximum reuse

B

New ecc_agents table (lightweight)

Dedicated table: id, name, role (operator|client), status, lastActiveAt, currentTopicId. Fully decoupled from company agent model. Seeded once, status updated by orchestrator.

Pros

  • Zero impact on existing agents infrastructure
  • Schema exactly matches ECC needs — no nulls, no unused columns
  • Orchestrator updates status directly (no inference from workflow_runs)

Cons

  • New table + migration + new service + new API route
  • ECC agents isolated — can't reuse agent budget/heartbeat machinery
C

Virtual agents — no DB, derived from ECC state

No new rows. Agent status is computed: if workflow_runs has an active ecc_conversation run → processing. Otherwise idle. A new API endpoint GET /ecc/agents returns the two virtual agents derived from live data.

Pros

  • Zero schema changes
  • Always accurate — no sync issues between agent record and actual state

Cons

  • No persistent "last active" or "current topic" — only live state
  • Can't store agent config/metadata (e.g. description, icon)
  • Feels hacky — agents aren't real entities
